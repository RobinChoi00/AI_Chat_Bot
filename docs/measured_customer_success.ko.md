**고객 성과 집계와 상담 흐름 운영 안내**

관리자 지표는 실제 저장된 관찰을 설명합니다. 대화가 길어졌거나 티켓이 닫혔다고
고객의 문제가 해결됐다고 판정하지 않습니다. 테스트 통과는 실제 고객 해결률의
측정과 구분합니다.

**Warranty 결과와 업무 진행**

고장·설치 상담은 최신 고객 관찰을 기준으로 해결 확인, 미해결 확인, 점검 불가,
보류, 결과 미확인을 구분합니다. `steps_completed`는 진행 기록이며 해결 응답의
분모에 넣지 않습니다. 나중에 다시 고장이라고 보고하면 최신 결과와 재발 집계에
반영합니다. 뒤로 이동해 결과를 철회하면 미확인으로 남기고, 재입력한 실제 선택을
최신 관찰로 기록합니다.

진단 완료는 실제 워크플로의 진단 종료 지점을 기준으로 합니다. 진단 전 사람 요청,
콜백 요청, 안전 문제에 따른 중단을 진단 완료로 올리지 않습니다. 사람 요청 저장과
직원의 수신·첫 응답은 별개입니다. 아직 직원 응답 이벤트를 측정하지 않는 채널은
미측정으로 표시합니다.

Delivery는 제품 고장의 해결률에서 분리합니다. 검증된 주문 조회, 조회 불가,
진행 보류를 따로 표시합니다. “나중에 진행”을 제품 수리 해결로 기록하지 않습니다.
배송 조회에는 주문번호와 주문 시 이메일이 모두 필요하며 같은 매장의 주문과
일치해야 합니다. 조회 시각과 배송사의 최종 스캔 시각은 서로 다릅니다.

기존 `Abandoned`는 설정된 시간 이상 멈춘 진행 중 상담을 뜻합니다. 표시를
“장기 미진행”으로 바꾸고 확정 이탈·실패와 구분합니다. 과거 고객 답변 역할에는
자동 흐름 선택도 포함되므로 저장 메시지 수만으로 고객의 실제 답변 횟수나 중단
원인을 단정하지 않습니다.

**Sales 성과와 전달 상태**

추천 요청이 기록된 상담만 추천 완료율의 분모로 사용합니다. 근거 있는 제품 추천과
조건에 맞는 제품을 확인할 수 없다는 정직한 결과를 함께 설명합니다. 추천 완료는
구매나 고객 문제 해결의 확인이 아닙니다.

명시적인 사람 요청은 추가 인터뷰를 강요하지 않고 요청 저장과 직접 연락 경로를
안내합니다. 확인된 Tidio 운영자 이벤트가 있는 경우에만 그 채널의 직원 참여를
집계합니다. 요청/리다이렉트 상태를 연결 완료로 표현하지 않습니다.

도움됨 평가는 평가 참여율과 표본 수를 함께 보여줍니다. 고객 발화가 두 번 이상인
`Engagement`는 참고 수치입니다. 반복 질문도 이 값을 올릴 수 있습니다. 질문 단계는
진행 중 대기·장기 미진행·답변 제공·사람 요청·상태 미확인을 구분하며, 후속 기록이
없다는 이유만으로 확정 이탈로 처리하지 않습니다.

리드 전달은 `pending`, SMTP 접수(`sent`), 실패(`failed`), 미확인 상태를 구분합니다.
SMTP 접수는 받은편지함 도착이나 직원의 확인·회신을 입증하지 않습니다. 새 전송은
설정 누락·인증 실패·연결 실패·수신자 거부 등의 비밀정보 없는 오류 코드로 기록하고,
TLS 방식과 제한 시간을 적용합니다. 과거 `smtp_returned_false` 기록만으로 당시의
실패 원인을 복원할 수 없습니다. 기존 실패 건은 자동 재발송하지 않습니다.

관리자는 Sales의 전달 상태와 현재 전송 설정 준비 여부를 확인한 뒤 기존 업무 절차로
실패 건을 점검합니다. 자격 증명 값은 관리자 응답이나 로그에 표시하지 않습니다.
SMTP 설정이 있다는 사실만으로 실제 발송 성공이 입증되는 것은 아닙니다.

이 전달 집계의 대상은 Sales API와 Tidio의 저장된 리드입니다. 별도 일반 채팅의
이전 이메일 도구는 이 리드 테이블에 저장하지 않으므로 해당 시도는 이 화면에서
미측정입니다. 관찰 범위를 전체 이메일이나 모든 고객 연락으로 확대 해석하지 않습니다.

**배포 버전별 비교**

기간(All time/최근 기간)과 별도로 전체·현재 릴리스 신규 상담·과거 버전 미확인·
복수 버전 상담을 선택할 수 있습니다. 새 상담이 생성된 트랜잭션에서 실제 코드
릴리스를 기록합니다. 기존 상담이 새 릴리스에서 이어지면 복수 버전으로 분류하며
현재 릴리스 신규 상담으로 소급하지 않습니다. 과거 원문과 기록은 삭제하지 않습니다.

운영 배포는 정확한 Git SHA를 `APP_RELEASE_ID`로 빌드·실행에 전달하며 코드 롤백 시
릴리스 식별자도 이전 SHA로 돌립니다. 이 식별자는 코드 배포 버전입니다. 운영 중
별도로 바뀌는 모델 설정이나 호스트 카탈로그 변경 전체를 동일한 식별자로 증명하지는
않습니다. 현재 모델·카탈로그 상태는 현재 실행 상태로 별도 표시합니다.

비교 시 신규 상담의 표본 수와 결과 미확인 비율을 함께 봅니다. 막 시작한 새 상담과
충분한 관찰 시간이 지난 과거 상담의 수치 차이를 곧바로 개선 효과로 해석하지 않습니다.
관찰 기간과 문의 목적이 유사한 상담끼리 비교해야 합니다.

**단계 관찰과 개인정보**

`conversation_releases`, `customer_journey_events`는 기존 DB에 추가되는 테이블입니다.
기록 동의 뒤의 화면 노출·진행·실패·건너뛰기·이어하기를 허용된 단계명과 이벤트로
기록합니다. 이벤트에 질문 원문·이메일·주문번호·추적 링크를 복사하지 않습니다.
서버가 저장한 관찰과 브라우저가 보고한 관찰은 구분합니다. 브라우저 이벤트를
실제 해결 결과나 직원 확인의 증거로 사용하지 않습니다.

단계별 수는 고유 세션 기준이며 서로 배타적인 고객 수가 아닙니다. 단계는 목적에
따라 생략·반복될 수 있습니다. 완료 이벤트가 없다는 것은 다음 관찰이 없다는 뜻이며
확정 이탈이 아닙니다. 동의 이전 방문은 이 측정에 포함하지 않습니다. 상담 생성 전에
남은 단계 관찰은 같은 세션·매장의 실제 상담이 생성되면 연결하며, 끝내 상담이 생성되지
않은 관찰은 전체 범위의 미연결 세션으로 남깁니다. 이를 특정 버전 신규 상담으로
추정하지 않습니다.

단계 집계는 이벤트 발생 시각, 상담 결과 집계는 상담 생성 기간을 기준으로 하므로
두 표의 분모가 다를 수 있습니다. 과거 화면별 노출·직원 첫 응답 시간·실제 체류시간은
기록이 없으면 복원하지 않습니다. 관찰이 없으면 0% 성과 대신 미측정 상태를 표시합니다.

**고객의 입력 부담과 이어하기**

웹 채팅은 기록 동의 후 연락처 이메일을 입력해야 시작할 수 있습니다. 이메일은 서버에
저장하고 접수 정보에 연결하며, 입력을 건너뛰어 상담을 시작할 수 없습니다. 같은 세션에
이메일이 저장되어 있으면 다시 요구하지 않습니다. 배송 조회에는 별도로 주문번호와
주문 당시 이메일을 확인합니다. 동의 후의 고지는 짧게 접어 원문을 열 수 있게 합니다.

사진·동영상은 제출 여부를 명확히 선택하게 하고, 마지막 접수 단계에서도 진행을
저장할 수 있게 합니다. 진행 저장은 실제 DB에 저장되며 서명된 이어하기 링크를
복사할 수 있습니다. 이메일은 발송 시도 예약 상태로 안내하고, 실제 SMTP 결과는
별도 기록합니다. 링크는 소지자가 상담을 이어갈 수 있는 임시 권한이므로 공개하지
않습니다. 연락처 이메일을 브라우저 저장소에 추가하지 않습니다.

**답변 신뢰성과 검증**

추천 조회 결과가 없으면 적합성·용량·메커니즘을 만들어내지 않습니다. 표 형식의
여러 모델 비교에서도 한 모델의 가격·용량을 다른 모델의 근거로 사용하지 않습니다.
배송 조회는 실제 도구의 고객용 결정적 응답을 사용하고, 입력 부족·오류·주문 미확인
상태에서 배송사·ETA·이동 상태를 추측하지 않습니다. 근거 오류나 조회 실패 결과는
일반 FAQ 캐시에 남겨 복구 이후에도 계속 재생하지 않습니다.

평가 자료는 회귀용과 독립 검증용을 구분합니다. 실제 과거 오류에서 만든 회귀 사례를
독립 검증 성과로 다시 세지 않습니다. 독립 검증 사례가 아직 없으면 실행은 명확히
실패하며 빈 집합을 통과로 보고하지 않습니다. 구조 검사·모의 API 검사·실제 모델
평가·실제 고객 해결률은 각기 다른 검증입니다.
