# 일상 워런티·세일즈 문의 시뮬레이션 v3

사용자가 설명한 실제 업무 유형에 맞춰 새 합성 대화를 작성했다. 워런티는 의자가 작동하지 않거나 부품이 고장 났다는 평범한 문의, 세일즈는 상품·비교·배송·설치·반품·결제·기존 주문의 다양한 문의를 중심으로 했다. 실제 고객 로그나 문의 빈도를 확보한 평가는 아니다.

**실제 격리 HTTP API 시나리오 144개: 98개 통과, 46개 개선 조건 미충족, 실행 오류 0개.** 모든 사례의 전체 요청·응답·저장 상태를 보존했다. 앱 코드는 이번에 변경하지 않았으며 이전 v2와 같은 소스다.

## 결과를 읽는 방법

OpenAI 키가 없어 규칙 기반·키워드 및 모델 호출 불가 시의 대체 경로를 실행했다. 특히 워런티의 자유 문장 이해 결과가 운영 환경의 실제 모델 응답과 같다고 단정할 수 없다. 이번 기록은 해당 대체 경로가 유지해야 할 기본 동작과 Sales 상담 로직의 개선 근거다.

통과는 HTTP 200 여부가 아니라 고객 질문에 맞는 응답, 올바른 모델·조건·업무 부서, 유효한 다음 단계를 기준으로 판단했다. 정상적인 확인 질문과 필요한 전문 상담원 연결은 허용했다. 자동으로 고장 경로를 진행하거나 보증을 승인하도록 요구하지 않았다.

실패는 모두 같은 정도의 문제는 아니다. 명확한 증상에 일반 메뉴를 제시한 것은 자동 이해의 마찰이고, 고객이 한 말을 반대로 확인 제안하거나 다른 모델 가격을 안내한 것은 내용 정확성 문제다. 표의 통과 수는 실제 고객 해결률이나 운영 정확도가 아니다. 실제 문의 빈도가 없으므로 임의의 가중치로 100점 종합 점수를 만들지 않았다.

| --- | ---: | ---: |
| 워런티: 첫 증상 접수 | 13 / 24 | 11 |

## 워런티에서 우선 개선할 부분

**첫 증상 접수를 강화하되, 정상적으로 작동하는 진단 흐름은 유지할 수 있다.** 고장 경로를 고객이 확인한 뒤의 후속 대화는 20/24 사례가 통과했다. 모델·티켓 유지, 뒤로 가기, 반복되는 불명확 입력에서 상담원 선택지 제공, 영어 상담원·콜백 요청, 진단 종료 후 자동 보증 승인·배송 확약 방지는 검증한 사례에서 정상 동작했다.

1. **일상적인 증상을 읽고 고장 확인을 제안하기.** `My chair will not turn on.`, `The chair stopped working yesterday.`, 사용 5분 뒤 정지, 온열이 따뜻하지 않음, 롤러 딸깍 소리 및 일부 한·스페인어 표현은 규칙 대체 경로에서 고장 유형을 제안하지 못했다. 이런 9개 사례는 일반적인 “설치·배송·고장 중 선택” 메뉴로 돌아갔다. 상담이 완전히 막혔다는 뜻은 아니지만 이미 설명한 증상을 활용하지 못했다.

2. **부정문과 점검 결과를 반대로 제안하지 않기.** 전원·케이블을 확인했고 “딸깍 소리가 없다”고 했는데 “딸깍 소리를 들었다”를, “퓨즈가 정상이다”고 했는데 “퓨즈가 끊어졌다”를 확인 선택지로 제안했다. 실제 경로가 자동 진행된 것은 아니지만 고객에게 잘못된 확인 버튼을 제시한다. 모델 호출이 불가능할 때도 부정 표현과 정상·고장 상태를 보존하도록 수정해야 한다.

3. **작업 목적과 부품 이름을 함께 보기.** “발받침을 어떻게 조립하나요?”는 설치인데 고장으로 제안됐다. “옆 패널 설치 도움”은 설치를 제안하지 못했다. 가죽 찢어짐은 외관 손상인데 일반 부품 메뉴 재질문으로 남았다. 부품 단어 하나보다 조립·설치·찢어짐·작동 불가 같은 행위를 함께 분류해야 한다.

4. **진행 중에도 상담원 요청을 즉시 처리하기.** 영어 요청은 통과했지만 `담당자와 상담하고 싶어요`는 리모컨 전원 질문을 반복했다. 고객 언어별로 동일한 상담원 요청 경로가 필요하다.

권장 흐름은 **증상 요약 → 필요한 모델 확인 → 문제 부위와 동작 상태 확인 → 확인된 안전한 기본 점검 → 고객의 해결 여부 확인 → 미해결 시 접수·담당 검토**다. 이미 알려준 모델이나 완료한 점검은 유지하고, 모호할 때만 추가로 묻는다. 이 과정은 무상 보증 승인과 구분한다.

## 세일즈에서 우선 개선할 부분

**모든 질문을 새 의자 추천 인터뷰로 보내지 않고, 질문의 목적을 먼저 나눠야 한다.** 구매 전 정책의 첫 답변은 비교적 잘 처리했지만, 기존 주문과 후속 질문에서 맥락을 잃는 사례가 많았다.

| 고객의 실제 질문 예시 | 관측한 문제 | 원하는 대응 |
| --- | --- | --- |
| 리모컨 화면이 검고 버튼이 안 돼요 | Black 색상 재고 확인과 모델·키 질문 | 리모컨 고장으로 이해하고 보증 서비스 경로 안내 |
| Titan TP-Epic 발 롤러가 멈췄어요 | 새 의자 추천을 위한 키 질문 | 기존 제품의 고장·부품 상담으로 분류 |
| Maestro LE 2.0 가격이 얼마예요? | 다른 모델인 구형 OS-Pro Maestro LE의 $8,999 안내 | 요청한 세대의 정확한 제품 ID 사용. 저장소의 LE 2.0 카탈로그 기준은 $7,999이며 실시간 판매가는 별도 확인 |
| Grande XL은 어떤 색상이 있어요? | 색상을 빼고 전체 스펙 출력 | 카탈로그 변형의 Black·Brown·Taupe 등 질문한 항목을 직접 답변 |
| Bluetooth나 Body Scanning이 있나요? | 다른 세대 또는 일반 사양만 안내 | 정확한 모델의 게시된 기능 자료를 구조화해 활용. 없는 자료는 확인 필요 안내 |
| Zero gravity가 무슨 뜻이에요? | 모델명부터 요구 | 일반 기능 설명을 먼저 제공 |
| 그럼 환불은 언제 들어오나요? | 고객 키를 묻는 추천 인터뷰 시작 | 이전 환불 문맥 유지, 확인 가능한 정책 또는 Sales 담당 확인 안내 |
| 의자를 받았는데 반품하고 싶어요 | 일반 문의 메뉴로 돌아감 | 구매 후 반품 요청으로 이해하고 Sales의 확인 절차 안내 |
| 주문한 색상을 바꾸고 싶어요 | Warranty 부서 안내 | Sales 주문 변경 담당으로 연결 |
| 출입문을 36이 아니라 28인치로 정정했어요 | 이전 36인치 유지 | 최신 고객 치수로 후보를 다시 검증 |

실행 순서는 다음이 타당하다.

1. **질문의 업무를 먼저 구분:** 상품 기능 문의 / 새 구매 추천 / 기존 제품 고장 / 구매 전 정책 / 기존 주문 처리. 고장 표현은 색상·재고·기능 키워드보다 먼저 해석한다.
2. **모델명·세대·옵션을 정확히 식별:** LE와 LE 2.0, Solo Flex와 Bravo Duo Flex 등을 임의로 바꾸지 않는다. 확신이 없으면 모델을 확인한다.
3. **질문한 항목부터 짧게 답변:** 색상·마사지 강도·Bluetooth·반품 배송비·보증 노동비 등 해당 항목을 먼저 제시하고, 관련 없는 전체 스펙이나 추천 인터뷰를 붙이지 않는다.
4. **후속 질문의 업무 맥락 유지:** “그럼 노동비는?”, “언제 환불돼요?”, “그 모델도 있어요?”는 직전 주제·모델·조건과 함께 해석한다. 반품 배송비를 일반 배송 설명으로 바꾸거나 환불을 신체 조건 질문으로 바꾸지 않는다.
5. **구매 후 업무는 적절한 팀과 확인 절차로:** 배송·취소·환불·청구서·주문 색상 변경은 Sales, 고장·부품·기술 지원은 Warranty로 구분한다. 실시간 권한이 필요한 처리는 승인·완료를 약속하지 않는다.
6. **추천은 모든 실제 사용자와 최신 조건을 검증:** 아버지 320lb·어머니 150lb가 함께 쓰는 의자에서 가벼운 사용자만 기준으로 삼지 않고, 변경된 출입문과 예산을 반영한다.

## 개선 후 수용 기준 예시

- “전원이 안 켜져요”를 받으면 필요한 모델을 확인한 뒤 전원 문제를 확인하는 질문으로 이어진다. 설치인지 고장인지 처음부터 다시 고르라고만 하지 않는다.
- “딸깍 소리가 안 나요”를 소리가 났다는 선택지로 뒤집지 않는다. 사용자가 완료한 점검 사실을 보존한다.
- “어떤 색상이 있어요?”에는 해당 모델의 색상 또는 확인 필요 여부를 답하고, 키·몸무게를 필수로 요구하지 않는다.
- LE 2.0 가격·기능 답변은 LE 2.0 자료에 연결되고, 다른 세대나 유사 이름 모델의 자료를 빌리지 않는다.
- 반품·환불 대화의 후속 질문은 해당 업무를 유지하며, 실제 접수·승인·송금 여부를 구분해 안내한다.
- 각 수정은 같은 API 대화와 새로운 비공개 변형 사례로 재검증하고, OpenAI가 연결된 격리 환경에서 실제 모델 응답을 별도로 평가한다.

## 범위와 재현

- 144개 시나리오 모두 전체 기록이 있고, 설정·상태 조회를 포함한 실제 HTTP 요청은 496회였다. 이는 고객 발화 횟수와 같지 않다.
- 사례는 처음 실패한 지점에서 중단할 수 있다. 기록에 없는 계획된 후속 질문까지 통과했다고 계산하지 않았다. Sales 주문·정책 모듈은 계획·실행·미실행 후속 질문 수도 별도로 기록한다.
- 사례마다 새 메모리 데이터베이스를 사용했다. 개인정보 동의·필수 연락처·모델 등록은 필요한 경우 정상적으로 수행한 후 대화를 검사했다.
- 실제 외부 전송 시도는 0회다. 라이브 재고·주문·이메일 성공을 가정하지 않았고, 필요한 담당 확인은 유효한 대응으로 인정했다.
- 실제 모델의 자연어 이해·답변 품질, 브라우저 화면, 운영 지연·부하·고객 해결률은 측정하지 않았다. `live_model_score`와 종합 업무 점수는 모두 `null`이다.
- 평가 기준 검토에서 올바른 확인 제안·명시적인 상담원 연결 버튼을 인정했고, 실제로 맞는 28인치 문 후보가 존재한다는 점도 반영했다. 실패를 숨기려고 앱을 변경하지 않았다.

```bash
.venv/bin/python script/simulate_customer_business_quality.py \
  --out /tmp/customer-business-audit-v3.json
.venv/bin/pytest -q tests/test_customer_business_audit.py
```
